하이버네이트 (Hibernate)
하이버네이트 (Hibernate)는 자바 객체 관계 매핑 (ORM) 프레임워크입니다. ORM은 객체 지향 프로그래밍의 객체와 관계형 데이터베이스의 테이블 간의 변환을 자동으로 처리해주는 기술입니다.
JPA(Java Persistence API)를 구현한 가장 유명한 프레임워크 중 하나로, 객체(Java 클래스)와 테이블(데이터베이스)을 연결해줍니다. 이를 통해 객체 지향적인 방식으로 데이터베이스 작업을 할 수 있게 해줍니다.

하이버네이트의 세션 객체 (Session)
하이버네이트에서 세션(Session) 객체는 하이버네이트 ORM의 핵심적인 인터페이스로, 데이터베이스와의 연결을 관리하고, 데이터베이스에서 엔터티 객체의 상태를 관리하는 역할을 합니다.

세션의 주요 역할
엔티티 저장/조회/삭제: 세션을 통해 객체를 데이터베이스에 저장하거나 조회할 수 있습니다.
트랜잭션 관리: 데이터베이스의 트랜잭션을 시작하고, 커밋하거나 롤백할 수 있습니다.
캐시 관리: 하이버네이트는 1차 캐시를 세션 단위로 관리합니다. 이는 같은 세션 내에서 동일한 엔터티에 대한 중복 조회를 방지하는 데 유용합니다.

세션의 주요 메서드
save(): 객체를 데이터베이스에 저장합니다.
get(), load(): 데이터베이스에서 객체를 조회합니다.
delete(): 객체를 데이터베이스에서 삭제합니다.
beginTransaction(), getTransaction(): 트랜잭션을 시작하고 관리합니다.

세션의 생명주기
열기: 애플리케이션이 실행되면 하이버네이트 세션을 열고, 데이터베이스와의 연결을 관리합니다.
사용: 데이터를 저장하거나 조회하는 작업을 처리합니다.
닫기: 작업이 끝난 후 세션을 닫고, 데이터베이스 연결을 종료합니다.

## 21. 다이렉트 페치 사용 방법

다이렉트 페칭 = ID로 가져오기  식별자(ID)를 알고있고, 지연 연관관계가 필요 없을 때 엔티티를 가져오는 바람직한 방법

@OneToMany, @ManyToMany는 지연로딩으로, @OneToOne, @ManyToOne은 즉시로딩으로 처리된다
- 즉시 연관관계의 엔티티를 다이렉트 페칭하면 불필요한 로딩으로 성능이 저하됨
- 지연 연관관계의 엔티티를 다이렉트 페칭하면 연관 엔티티를 사용해야할 때 추가 쿼리가 발생하여 성능이 저하됨
- 따라서 최선은 모든 연관관계를 지연으로 유지하고, 해당 연관관계 로드를 위해 수동 페치를 사용하는 것
- 현재 영속성 콘텍스트에서 지연 연관관계 참조 계획이 없을때만 다이렉트 페치 사용

#### EntityManager를 통한 다이렉트 페치
@PersistenceContext를 통해 EntityManager 주입  
EntityManager가 있으면 나머지는 find() 메서드 호출만 하면 됨, Optional 반환
```
@PersistenceContext
private EntityManager entityManager;

@Override
public Optional<T> find(Class<T> clazz, ID id) {
    if (id == null) {
        throw new IllegalArgumentException("ID cannot be null");
    }

    return Optional.ofNullable(entityManager.find(clazz, id));
}
```
-> 내부 sql문은 findById와 동일

#### 하이버네이트 Session을 통한 다이렉트 페치
하이버네이트 Session.get() 메서드를 사용하려면 EntityManager에서 Session을 Unwrap해야함  
아래는 Unwrap 수행하고 Optional 반환
```
@PersistenceContext
private EntityManager entityManager;

@Override
public Optional<T> findViaSession(Class<T> clazz, ID id) {
    if (id == null) {
        throw new IllegalArgumentException("ID cannot be null");
    }

    Session session = entityManager.unwrap(Session.class); // Hibernate의 세션 객체를 가져옴

    return Optional.ofNullable(session.get(clazz, id));
}
```
-> findById, EntityManager.find와 동일

JPA 영속성 공급자는 다음 순서로 다이렉트 페칭을 하며 순서는 엄격히 처리된다
- 현재 영속성 콘텍스트 (1차 캐시, 영속성 컨텍스트 내부 엔티티를 보관하는 저장소)
- 애플리케이션 캐시 (2차 캐시, 공유캐시)
- 데이터베이스

#### 다이렉트 페치 및 세션 수준 반복 읽기
현재 영속성 콘텍스트에서의 탐색

하이버네이트가 다이렉트 페치에서 영속성 콘텍스트를 우선 조회하는 이유는 세션 수준 반복 읽기(session-level repeatable reads) 보장  
처음 가져온 엔티티는 영속성 컨텍스트에 캐시, 동일한 엔티티 조회는 1차 영속성 콘텍스트에서 수행됨을 의미  
세션 수준 반복 읽기는 동시 쓰기 처리시 업데이트 손실 방지
```
@Transactional(readOnly=true)
public void directFetching() {
    // 스프링 데이터를 통한 다이렉트 페치
    Optional<Author> resultSD = authorRepository.findById(1L);
    System.out.println("Direct fetching via Spring Data result: " + resultSD.get());

    // EntityManager를 통한 다이렉트 페치
    Optional<Author> resultEM = dao.find(Author.class, 1L);
    System.out.println("Direct fetching via EntityManager result: " + resultEM.get());

    // Session를 통한 다이렉트 페치
    Optional<Author> resultHS = dao.findViaSession(Author.class, 1L);
    System.out.println("Direct fetching via Session result: " + resultHS.get());
}
```

@Repository
@Transactional(readOnly = true)
public interface AuthorRepository extends JpaRepository<Author, Long> {
    @Query("SELECT a FROM Author a WHERE a.id = ?1")
    Optional<Author> fetchById(long id);

    @Query("SELECT a FROM Author a WHERE a.id = ?1")
    Author fetchByIdJpql(long id);

    @Query(value = "SELECT * FROM author WHERE id = ?1", nativeQuery = true)
    Author fetchByIdSql(long id);

    @Query("SELECT a.name FROM Author a WHERE a.id = ?1")
    String fetchNameByIdJpql(long id);

    @Query(value = "SELECT name FROM author WHERE id = ?1", nativeQuery = true)
    String fetchNameByIdSql(long id);

MySQL에서 기본 격리 수준은 REPEATABLE_READ -> 트랜잭션 A가 시작될 때 읽은 데이터는 트랜잭션이 끝날 때까지 변경되지 않음, 트랜잭션 A는 트랜잭션 B의 영향을 받지 않음  
격리 수준을 READ_COMMITED로 변경 -> 트랜잭션 내에서 읽은 데이터가 다른 트랜잭션에 의해 변경될 수 있음  
코드에서 격리 수준을 설정하지는 않고 전파행동만 정의 PROPAGATION_REQUIRES_NEW -> 트랜잭션 A와 B가 다른 영속성 컨텍스트에서 실행됨

트랜잭션 A
- findById -> ID 1인 저자 SELECT를 통해 가져와 영속성 컨텍스트 A에 로드  
트랜잭션 B
- 새로은 트랜잭션, 새로은 영속성 컨텍스트 -> SELECT를 통해 ID 1인 저자 B에 로드
- 이름 수정, 커밋 직전 flush 시점에 데이터베이스에서 실행 -> 이름 Alicia Tom  
트랜잭션 A
- findById : A에서 로드 -> 이름 Mark Jane; 세션 수준 반복 읽기 작동  
- fetchByIdJpql : JPQL 쿼리 실행하나 SELECT에 의한 데이터 스냅샷 무시, A에서 로드-> 이름 Mark Janet; 세션 수준 반복 읽기 작동  
- fetchByIdSql : SQL 쿼리 실행하나 SELECT에 의한 데이터 스냅샷 무시, A에서 로드-> 이름 Mark Janet; 세션 수준 반복 읽기 작동  
- fetchNameByIdJpql : JPQL 쿼리 프로젝션 실행하여 데이터 스냅샷 가져옴-> 이름 Alicia Tom; 세션 수준 반복 읽기 작동안함
- fetchNameByIdSql : 네이티브 SQL 쿼리 프로젝션 실행하여 데이터 스냅샷 가져옴-> 이름 Alicia Tom; 세션 수준 반복 읽기 작동안함

하이버네이트 세션 수준 반복 읽기는 JPQL 또는 네이티브 SQL로 표현된 SQL 쿼리 프로젝션에 대해서는 동작하지 않고 항상 최신 데이터베이스 상태를 로드함  
트랜잭션 격리 수준을 REPEATABLE_READ로 변경하면 SQL 쿼리 프로젝션이 Mark Janet을 반환; 트랜잭션에게 여러 읽기에서 동일한 결과를 가져오도록 명시하기 때문  
REPEATABLE_READ가 세션 수준 반복 읽기 불가 현상을 방지하여, 데이터베이스에서 하나의 레코드를 여러번 읽는 트랜잭션에서 매번 동일한 결과를 얻음

#### ID로 여러 엔티티 다이렉트 페치
IN 연산자를 사용한 쿼리 활용

```

2. JPQL을 통해 결과 반환
```
@Query("SELECT b FROM Book b WHERE b.id IN ?1")

```

실행 계획 캐시(Execution Plan Cache)를 지원하는 데이터베이스와 IN을 사용하면 최적화 가능
- 동일한 쿼리가 여러 번 실행될 때 매번 새로운 실행 계획을 생성하지 않고 캐시된 실행 계획을 재사용
- 대부분 데이터베이스 지원

3. Specification 사용도 가능
```

public void fetchByMultipleIdsSpec() {
    List<Book> books = bookRepository.findAll(

// specs
// Specification : 
public class InIdsSpecification implements Specification<Book> {
    private final List<Long> ids;

    public InIdsSpecification(List<Long> ids) {
        this.ids = ids;
    }

    @Override
    public Predicate toPredicate(Root<Book> root,
                                 CriteriaQuery<?> cquery, CriteriaBuilder cbuilder) {
        return root.in(ids);

        // 또는
        // Expression<String> expression = root.get("id");
        // return expression.in(ids);
    }
}
```
Specification 인터페이스
- Spring Data JPA에서 제공하는 API
- 복잡한 조건, 다양한 조합의 필터링 로직 
- 해당 인터페이스 사용해서 동적 쿼리 생성

root: 'Root<Some>' 타입으로, 쿼리의 루트 엔티티를 나타냄, 쿼리 대상 엔티티의 필드에 접근할 때 사용
cquery: 'CriteriaQuery<?>' 타입으로, 쿼리 자체를 구성할 때 사용
cbuilder: 'CriteriaBuilder'타입으로, 쿼리의 조건을 생성하는데 사용되는 다양한 메서드를 제공

위 세 가지 방식은 동일한 SQL select 쿼리를 생성하고, 세션 수준 반복 읽기를 수행한다.

다른 접근 방법으로는 하이버네이트의 MultiIdentifierLoadAccess 인터페이스 사용이 있다.
- ID별로 여러 엔티티 배치(withBatchSize())로 로드 가능
- 쿼리 실행 전에 영속성 컨텍스트 검사 여부 지정 가능  
default : 검사하지 않음  
enabledSessionCheck() : 해당 메소드를 통해 활성화
- 하이버네이트 전용 API이므로 스프링 부트 스타일로 구성해야함
```
// MultipleIdsRepositoryImpl.java
import org.hibernate.MultiIdentifierLoadAccess;
import org.hibernate.Session;

@Repository
@Transactional(readOnly = true)
public abstract class MultipleIdsRepositoryImpl<T, ID extends Serializable>
        implements MultipleIdsRepository<T, ID> {

    @PersistenceContext
    private EntityManager entityManager;

    private final Class<T> entityClass;

    public MultipleIdsRepositoryImpl(Class<T> entityClass) {
        this.entityClass = entityClass;
    }

    @Override
    public List<T> fetchInBatchesByMultipleIds(List<ID> ids, int batchSize) {
		// 여러 개의 ID를 받아 지정된 배치 크기로 데이터를 가져옴
		// 최대 batchSize 개수만큼으 ID를 데이터베이스에 가져옴
		// 예를 들어 총 id의 개수가 200개, batchSize가 50개이면 4번에 나눠서 조회가 이루어짐
        List<T> result = getMultiLoadAccess().withBatchSize(batchSize).multiLoad(ids);

        return result;
    }

    @Override
    public List<T> fetchBySessionCheckMultipleIds(List<ID> ids) {
		// 세션 체크를 활성화한 상태로 여러 개의 ID 데이터를 가져옴
        List<T> result = getMultiLoadAccess().enableSessionCheck(true).multiLoad(ids);

        return result;
    }

    @Override
    public List<T> fetchInBatchesBySessionCheckMultipleIds(List<ID> ids, int batchSize) {
		// 세션 체크를 활성화하고 배치 크기를 설정하여 여러 개의 ID 데이터를 가져옴
        List<T> result = getMultiLoadAccess().enableSessionCheck(true)
                .withBatchSize(batchSize).multiLoad(ids);

        return result;
    }

    private MultiIdentifierLoadAccess<T> getMultiLoadAccess() {
		// EntityManager를 Hibernate Session으로 변환하여 MultiIdentifierLoadAccess 객체 반환
        Session session = entityManager.unwrap(Session.class);

        return session.byMultipleIds(entityClass);
    }

}
```

## 22. 미래 영속성 컨텍스트에서 데이터베이스 변경 사항 전파를 위해 읽기 전용 엔터티을 사용하는 이유
시나리오는 아래와 같다.  
> Author 엔터티에 id, name, age, genre 속성이 있다.  
> 저자의 프로필을 로드하고 편집한 다음 다시 저장한다.  
> 단일 트랜잭션으로 처리하지 않고 2개의 서로 다른 트랜잭션에서 수행한다.

#### 읽기-쓰기 모드로 Author 로드
읽기-쓰기 모드로 로드한다고 가정한다.
```
@Transactional
public Author fetchAuthorReadWriteMode() {
    Author author = authorRepository.findByName("Joana Nimar");
    return author;
}
```
트랜잭션 안에서 로드 및 반환만 되므로, 수정 전에 현재 영속성 컨텍스트가 닫히고 반환된 Author는 분리된다.
다음은 읽기-쓰기 엔터티를 가져온 후 영속성 콘텍스트 정보이다.
(collection entries : 엔티티 필드 중 Collection 타입으로 선언된 부분을 관리, 엔티티간의 관계 관리를 위해 사용)
```
managed entities : 1
collection entries : 0

EntityKey[com.bookstore.entity.Author#4]:
	Author{id=4, age=34, name=Joana Nimar, genre=History}
EntityName: com.bookstore.entity.Author
Status: MANAGED
State: [34, History, Joana Nimar]
```
엔티티가 MANAGED 상태이고 Hydrated 상태이다.
- Managed 상태 : 영속성 컨텍스트에 의해 관리되고 있는 상태
- Hydrated 상태 : 캐시 상에 엔티티를 객체가 아닌 Object[]로 보관한 상태. 개별 속성이 Object들로 분리돼있어 Disassembled 상태라고도 함  
=> JPA의 핵심 기능인 변경 감지, 지연 로딩, 캐싱, 데이터 동기화를 활용할 수 있는 상태

이 방식은 2가지 단점이 있다.
- 하이버네이트는 엔티티 변경을 데이터베이스로 전파할 준비가 되어있으므로, 변경이 없음에도 메모리에 hydrated 상태가 유지됨
- 하이버네이트는 flush 시점에 수정 처리를 위해 엔티티를 스캔하는데, 변경이 없음에도 이 엔티티가 스캔에 포함됨  
불필요한 Hydrated 상태로 저장하면 메모리가 더 소모되고, 불필요한 스캔을 하고 가비지 컬렉터가 이를 수집해 CPU 리소스가 소모된다. 따라서 읽기 전용 모드를 사용해야 한다.  

#### 읽기 전용 모드로 Author 로드
Author 엔티티는 현재 영속성 콘텍스트에서 수정되지 않으므로 다음과 같이 읽기 전용 모드로 로드
```
@Transactional(readOnly = true)
public Author fetchAuthorReadOnlyMode() {
    Author author = authorRepository.findByName("Joana Nimar");
    return author;
}
```
> 위에서 로드되는 것은 DTO(프로젝션)이 아닌 읽기 전용 엔티티이다.  
읽기 전용 엔티티는 현재 영속성 컨텍스트에서는 변경이 반영되지 않지만, 이후 다른 영속성 컨텍스트에서 관리되면 변경이 데이터베이스로 전파될 수 있다.  
반면 DTO는 영속성 컨텍스트에 로드되지 않으며, 수정되지 않는 데이터에 적합하다.  
다음은 읽기 전용 엔티티를 가져온 후 영속성 콘텍스트 정보이다.
```
managed entities : 1
collection entries : 0

EntityKey[com.bookstore.entity.Author#4]:
	Author{id=4, age=34, name=Joana Nimar, genre=History}
EntityName: com.bookstore.entity.Author
Status: READ_ONLY
State: null
```
READ_ONLY 상태이며 Hydrated 상태가 무시되었다. 자동 flush 시간이 없고 더티 체킹을 하지 않는다. 따라서 메모리 및 CPU의 소모를 줄일 수 있다. 

#### Author 수정
엔티티를 읽어와서 반환한 후 분리되는데, 이후에 수정 및 병합을 할 수 있다.
```
// 분리된 상태에서 읽기 전용 엔티티 수정
Author authorRO = bookstoreService.fetchAuthorReadOnlyMode();
authorRO.setAge(authorRO.getAge() + 1); // authorRO는 준영속 상태로 JPA는 더티체킹 하지 않음
bookstoreService.updateAuthor(authorRO);

// 엔티티 병합
@Transactional
public void updateAuthor(Author author) {
	// 내부에서 EntityManager#merge() 호출
    authorRepository.save(author);
}
```
persist와 merge의 차이
- persist : 새로운 entity인 경우 사용, 이 경우 리턴된 객체 필드를 사용하지 않아도 된다.
- merge : persist 상태였다가 detached된 상태에서 다시 persist 상태가 될 때 merge함, 이 경우 반드시 리턴된 결과를 통해서 다음 작업을 진행해야 EntityManager가 관리하는 상태를 추적할 수 있다.  
참고로 merge 내부에서는 준영속 상태의 엔티티를 복사하여 새로운 영속(managed) 상태의 엔티티를 생성한다.

읽기 전용 트랜잭션에서 가져온 엔티티는 준영속(detached) 상태가 되므로, 이를 직접 수정해도 데이터베이스에 반영되지 않는다.  
변경 사항을 반영하려면 merge를 사용하여 영속성 컨텍스트에서 엔티티를 다시 관리해야 한다.  

위 시나리오는 웹 어플리케이션에서 일반적으로 발생한다. 이런 시나리오에서는 2개 이상의 HTTP 요청이 필요하다. 첫번째 요청은 저자의 프로필을 로드하고, 두번째 요청은 프로필 변경 사항을 저장한다. 두 요청 사이에는 저자가 변경할 내용을 생각하는 시간이 있을 수 있는데 이 내용은 뒤에서 설명한다.

## 23. 하이버네이트 Bytecode Enhancement를 통한 엔티티 속성 지연 로딩 방법
```
@Entity
public class Author implements Serializable {
    private static final long serialVersionUID = 1L;

    @Id
    private Long id;

    @Lob
    @Basic(fetch = FetchType.LAZY)
    private byte[] avatar;

    private int age;
    private String name;
    private String genre;
	
	// getter/setter 생략
```

#### 속성 지연 로딩 활성화
엔티티의 식별자(id), name, age, genre 등의 속성은 로딩 즉시 가져와도 되지만, avatar는 지연 방식으로 가져와야 한다. 따라서 Author 호출 시 트리거된 SQL에 avatar 컬럼은 없어야한다. avatar는 그림을 나타내므로 많은 바이트 데이터를 갖기 때문에 성능 저하를 가져온다. 따라서 속성 지연 로딩을 사용한다.
> 속성 지연 로딩 : CLOM, BLOB, VARBINARY 등 대용량 데이터를 저장하는 컬럼 타입을 호출하는 경우, 또는 별도 요청 시 세부 정보가 로드돼야 하는 경우에 유용하다.  

속성 지연 로딩을 사용하려면 아래와 같은 단계로 사용한다.
1. 설정 추가
- Maven에 하이버네이트 Bytecode Enhancement 플러그인 추가
- enableLazyInitialization 설정을 통해 지연 초기화 활성화 -> 엔티티 클래스의 바이트 코드를 계측하도록 하이버네이트에 지시
- Maven의 경우 아래와 같이 pom.xml에 추가
```
<plugins>
	...
    <plugin> 
        <groupId>org.hibernate.orm.tooling</groupId> 
        <artifactId>hibernate-enhance-maven-plugin</artifactId> 
        <version>${hibernate.version}</version> 
        <executions> 
            <execution> 
                <configuration> 
                    <failOnError>true</failOnError> 
                    **<enableLazyInitialization>true</enableLazyInitialization>**
                </configuration> 
                <goals> 
                    <goal>enhance</goal> 
                </goals> 
            </execution> 
        </executions> 
    </plugin>
	...
</plugins>
```

2. @Basic(fetch = FetchType.Lazy)로 지연 로딩할 속성에 어노테이션 지정
```
@Basic(fetch = FetchType.LAZY)
private byte[] avatar;
```
> @Basic 만 지정하면 기본 fetch 정책(eager)을 따름  
> 영속성 컨텍스트 외부에서 지연 속성을 가져오려고 하면 LazyInitializationException이 발생한다.  

#### 속성 지연 로딩과 N+1
N+1은 예상보다 많은 쿼리가 실행되면서 발생하는 성능 저하 문제(cpu, ram 메모리, 데이터베이스 커넥션 등)이다.  
아래 코드를 살펴보자
```
    @Transactional(readOnly = true)
    public List<Author> fetchAuthorsDetailsByAgeGreaterThanEqual(int age) {
        List<Author> authors = authorRepository.findByAgeGreaterThanEqual(40);

        // N+1 케이스이므로 피해야 한다.
        authors.forEach(a -> {
            a.getAvatar();
        });

        return authors;
    }
```
위 코드에서는 아바타가 지연 속성이므로 가져온 저자의 수 만큼 getAvatar 내부 쿼리를 추가 실행시킨다.  

서브엔티티(Subentities) 기술 또는 DTO로 지연 로딩 속성을 명시적으로 처리하는 Select 쿼리를 트리거해 성능 저하를 피할 수 있다.
```
// DTO
public interface AuthorDto {
    String getName();
    byte[] getAvatar();
}

@Transactional(readOnly = true)
@Query("SELECT a.name AS name, a.avatar AS avatar FROM Author a WHERE a.age >= ?1")
List<AuthorDto> findDtoByAgeGreaterThanEqual(int age);
```

#### 속성 지연 로딩과 지연 초기화 예외(LazyInitializationException)
스프링 부트에서 속성 지연 로딩을 활성화하면 지연 초기화 예외가 발생할 수 있다. 보통 Open Session In View(OSIV)를 비활성화할 때 발생한다.
> Jackson : 스프링 부트 기본 JSON 라이브러리. Jackson 사용 시 영속성 콘텍스트가 종료된 후 지연 속성에 접근하려고 하면 exception 발생. 하이버네이트 세션이 없는 상태에서 지연로드된 속성을 강제 초기화 하기 때문  
> OSIV : 데이터베이스 세션을 HTTP 요청의 시작부터 끝까지 열어 두는 방식, 해당 패턴의 주 목적이 지연 로딩 문제 해결이다.  영속성 콘텍스트가 뷰 렌더링까지 유지되므로 안전하게 사용할 수 있음. 그러나 커넥션 풀을 계속 잡고 있으므로 성능 저하를 발생시킬 수 있다. 원격 서비스를 많이 호출하거나 트랜잭션 컨텍스트 외부에서 많은 일이 발생하는 경우 OSIV를 모두 비활성화하는 것이 좋다.  

OSIV를 비활성화한 상태에서 Jackson 사용 시 지연 초기화 예외가 발생하는 문제를 해결하는 방법은 2가지이다.

1. 지연 로드 속성에 대한 명시적 기본값 설정
```
@Transactional(readOnly = true)
public Author fetchAuthor(long id) {
   Author author = authorRepository.findById(id).orElseThrow();

    if (author.getAge() < 40) {
        author.getAvatar(); // 지연 로딩 속성을 초기화
    } else {
        author.setAvatar(null); // 명시적 null 설정
    }

    return author;
}
```
```
import com.fasterxml.jackson.annotation.JsonInclude;
import com.fasterxml.jackson.annotation.JsonInclude.Include;

// ...

@Entity
@JsonInclude(Include.NON_DEFAULT)
public class Author implements Serializable {
	// ...
}
```
@JsonInclude(Include.NON_DEFAULT)를 사용하면 필요 없는 속성을 JSON에서 제거해 클라이언트에 더 간결한 데이터를 전달할 수 있습니다.

>1. fetchAuthor 메서드 실행:
>Author 엔티티를 조회하며 트랜잭션이 활성화된 상태.
>조건에 따라 author.getAvatar()를 호출해 지연 로딩 속성을 초기화하거나, author.setAvatar(null)로 설정
>
>2. 트랜잭션 종료:
>메서드가 종료되면서 트랜잭션도 종료되고, 영속성 컨텍스트가 닫힘.
>반환된 Author 객체는 준영속 상태가 됨.
>
>3. Jackson 직렬화:
>Author 객체를 JSON으로 직렬화.
>avatar 속성이 이미 초기화되었거나 null로 설정되어 있으므로, LazyInitializationException이 발생하지 않음.  

2. 커스텀 Jackson 필터 사용
직렬화해야하는 속성과 하지 않아도 되는 속성을 구분하는 커스텀필터 사용
```

```

```
@JsonFilter로 엔티티에 어노테이션 지정한다. AuthorId는 참조에 사용되는 필터의 식별자 역할을 한다.
AuthorId로 식별된 필터는 아래와 같이 구현된다.
```
@RestController
public class BookstoreController {
    private final SimpleFilterProvider filterProvider;
    private final BookstoreService bookstoreService;

    public BookstoreController(BookstoreService bookstoreService) {
        this.bookstoreService = bookstoreService;

        filterProvider = new SimpleFilterProvider().addFilter("AuthorId",
                SimpleBeanPropertyFilter.filterOutAllExcept("id", "name", "age", "genre")); // 중요, 전달되어야하는 속성 명시. 지연 속성(avatar)은 제외됨
        filterProvider.setFailOnUnknownId(false);
    }
    
    // ...
}
```
필터는 다음과 같이 REST 엔드포인트에서 사용된다.
```
@GetMapping("/authors/{age}")
public MappingJacksonValue fetchAuthorsByAgeGreaterThanEqual(@PathVariable int age)
        throws JsonProcessingException {
    List<Author> authors = bookstoreService.fetchAuthorsByAgeGreaterThanEqual(age);

    MappingJacksonValue wrapper = new MappingJacksonValue(authors); // 중요
    wrapper.setFilters(filterProvider);
    return wrapper;
}
```
MappingJacksonValue가 반환되어 다음과 같이 직렬화된다.
```

    "id": 1,
    "age": 43,
    "name": "Martin Ticher",
    "genre": "Horror"
}
```
>1. @JsonFilter와 필터 적용:
>@JsonFilter("AuthorId")는 직렬화 시 특정 속성만 포함하도록 필터링을 정의
>SimpleFilterProvider와 SimpleBeanPropertyFilter를 통해 id, name, age, genre 속성만 직렬화 대상에 포함되도록 설정함
>지연 로딩(Lazy Fetch) 속성은 직렬화 대상에서 제외되므로 Jackson이 지연 로딩 속성을 초기화 하지 않음
>
>2. MappingJacksonValue 사용:
>REST 컨트롤러에서 MappingJacksonValue를 반환하면서 필터 적용
>필터가 설정된 엔티티 속성만 직렬화되므로, 지연 초기화가 필요한 속성에 접근하지 않아 LazyInitializationException이 발생하지 않는다.  

하지만 애플리케이션이 avatar 속성을 가져온 경우에 대해서도 처리하지 않으면 `Cannot resolve PropertyFilter with id AuthorId`예외가 발생함. 즉 필터가 모든 속성을 직렬화해야함.
```
@Configuration
public class WebConfig extends WebMvcConfigurationSupport {
    @Override
    protected void extendMessageConverters(List<HttpMessageConverter<?>> converters) {
        for (HttpMessageConverter<?> converter : converters) {
            if (converter instanceof MappingJackson2HttpMessageConverter) {
                ObjectMapper mapper = ((MappingJackson2HttpMessageConverter) converter).getObjectMapper();
                mapper.setFilterProvider(new SimpleFilterProvider().addFilter("AuthorId", SimpleBeanPropertyFilter.serializeAll())); // 중요
            }
        }
    }
}
```
특정 엔드포인트에 필터를 설정하는 것이 아니라 모든 HTTP 응답에서 해당 필터를 적용하는 방법이다.

## 24. 서브엔티티를 통한 엔티티 속성 지연 로딩 방법
```
@Entity
public class Author {
    private static final long serialVersionUID = 1L;

    @Id
    private Long id;

    @Lob
    private byte[] avatar;

    private int age;
    private String name;
    private String genre;

    // getter, setter 생략
}
```
이 방법 역시 avatar를 지연 방식으로 처리한다. 아래 그림과 같이 엔티티를 서브엔티티로 분리하는 방법이다.  

![이미지](https://media.springernature.com/lw685/springer-static/image/chp%3A10.1007%2F978-1-4842-5626-8_3/MediaObjects/487471_1_En_3_Fig2_HTML.jpg)  
중앙의 기반클래스(base class)는 엔티티가 아니고 데이터베이스 테이블도 없다.  
기반 클래스를 상속받는 자식클래스에게, 기반 클래스의 칼럼만 매핑정보로 제공한다.
위 그림의 BaseAuthor는 즉시 로딩 속성을 관리하며, BaseAuthor 의 하위 클래스는 이런 속성을 상속하는 엔티티 이다.
```
@MappedSuperclass
public class BaseAuthor implements Serializable {
    private static final long serialVersionUID = 1L;

    @Id
    private Long id;

    private int age;
    private String name;
    private String genre;

    // getter, setter 생략
}
```

AuthorShallow는 BaseAuthor의 서브엔티티로 상위 속성 모두 상속되어 즉시 로드됨.
@Table 어노테이션으로 서브엔티티를 author 테이블에 명시적으로 매핑하는 것이 중요
```
@Entity
@Table(name = "author")
public class AuthorShallow extends BaseAuthor {
}
```

AuthorDeep도 서브 엔티티이다. 상위 속성 모두 상속하고 추가로 아바타를 정의한다.
```
@Entity
@Table(name = "author")
public class AuthorDeep extends BaseAuthor {
    @Lob
    private byte[] avatar;

    public byte[] getAvatar() {
        return avatar;
    }

    public void setAvatar(byte[] avatar) {
        this.avatar = avatar;
    }
}
```
서브엔티티를 테이블로 명시적 매 하지 않으면 속성이 다른 테이블에 배치되고 상속된 속성들이 중복된다.
예를 들어, @Table(name = "author")이 없으면 ID, name, age, genre가 author_shallow, author_deep 테이블에 포함되며 avatar는 author_deep 테이블에 포함된다.

이 방법으로 Avatar는 필요에 따라 불러올 수 있게되었다. 이후에는 2개의 서브엔티티에 대한 레포지토리를 제공하면 된다.
```
@Repository
public interface AuthorShallowRepository extends JpaRepository<AuthorShallow, Long> {
}
```
```
@Repository
public interface AuthorDeepRepository extends JpaRepository<AuthorDeep, Long> {
}
```
AuthorShallowRepository의 findAll()을 호출하면 아래 SQL이 실행된다.
```
SELECT 
	authorshal0_ .id, 
	authorshal0_ .age, 
	authorshal0_ .	genre, 
	authorshal0_ .name
FROM author authorshal0_
```
AuthorDeppRepository의 findAll()을 호출하면 아래 SQL이 실행된다.
```
SELECT 
	authordeep0_ .id, 
	authordeep0_ .age, 
	authordeep0_ .genre, 
	authordeep0_ .name,
	authordeep0_.avatar
FROM author authordeep0_
```

> 결론을 다음과 같이 낼 수 있다.
> - 하이버네이트는 지연 로딩을 지원한다.
> - 이를 위해서는 Bytecode Enhancement가 필요하며, OSIV와 Jackson 직렬화 문제를 처리해야한다.
> - 서브엔티티 사용은 Bytecode Enhancement가 필요하지 않고 여러 문제가 발생하지 않으므로 더 적절하다고 볼 수 있다.

## 25. 스프링 프로젝션을 통한 DTO 가져오기
1. 데이터베이스에서 가져온 데이터 처리  
데이터베이스에서 가져온 데이터는 Hibernate의 영속성 컨텍스트(1차 캐시)에 저장되어 객체로 변환되고, Hydration 과정을 통해 관리된다.
2. 읽기 전용 모드  
읽기 전용 트랜잭션(@Transactional(readOnly = true))을 사용하면 메모리와 CPU 리소스를 절약할 수 있으며, Hibernate는 더티 체킹과 flush 비활성화하여 성능을 최적화한다.
3. DTO 사용  
읽기 전용 데이터를 처리할 때는 수정이 필요 없는 데이터를 DTO로 변환해 사용하는 것이 좋다. DTO는 필요한 속성만 포함시켜 불필요한 데이터 로딩을 방지함
4. 성능 최적화  
DTO에는 필요한 속성만 포함하고, LIMIT를 사용해 불필요한 데이터 로딩을 최소화해야한다.  

DTO와 스프링 프로젝션은 *메소드 호출 수를 줄이기 위해 프로세스간 데이터를 전달하는 객체* 라는 동일한 목적을 갖는다. 단 구현 수준에서는 다르다.
- DTO : 생성자, getter/setter가 있는 클래스에 사용
- 스프링 프로젝션 : 인터페이스와 자동 생성 프록시 사용, DTO 프로젝션  

```
@Entity
public class Author implements Serializable {
    private static final long serialVersionUID = 1L;

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String genre;
    private int age;

    // getter/setter 생략
```
목표는 동일한 genre를 가진 저자 2명의 name, age를 가져오는 것이다 -> 스프링 프로젝션 사용
스프링 프로젝션은 데이터베이스에서 가져와야 하는 컬럼에 대한 getter만 포함하는 자바 인터페이스로 시작; 인터페이스 기반 닫힌 프로젝션, 아래가 예제이다.
```
public interface AuthorNameAge {
    // 조회할 필드를 getter 형식으로 지정하면 해당 필드만 선택해서 조회
    String getName();
    int getAge();
}
```
```
// 레포지토리 인터페이스
@Repository
public interface AuthorRepository extends JpaRepository<Author, Long> {
    @Transactional(readOnly = true)
    List<AuthorNameAge> findFirst2ByGenre(String genre);

    // 프로젝션 인터페이스 -> 레포지토리 인터페이스 내부 선언
    interface AuthorNameAge {
        String getName();
        int getAge();
    }
}
```

이 프로젝션에서 2명의 저자만 가져오려면
```
import com.bookstore.projection.AuthorNameAge;

// ... 

@Repository
@Transactional(readOnly = true)
public interface AuthorRepository extends JpaRepository<Author, Long> {

```

#### JPA 네임드(네이티브) 쿼리 및 스프링 프로젝션 결합 사용
네임드 쿼리 : 미리 정의한 쿼리에 이름을 부여하여 사용하며, 정적 쿼리이다. 어노테이션 또는 XML 문서에 정의
```
// NamedQuery (JPQL 기반)
@NamedQuery(
        name = "Author.fetchName",
        query = "SELECT a.name FROM Author a"
)
@NamedQuery(
        name = "Author.fetchNameAndAge",
        query = "SELECT a.age AS age, a.name AS name FROM Author a"
)
@Entity
public class Author implements Serializable {
    // ...
}
```
```
// NamedNativeQuery (SQL 기반)
@NamedNativeQuery(
        name = "Author.fetchName",
        query = "SELECT name FROM author"
)
@NamedNativeQuery(
        name = "Author.fetchNameAndAge",
        query = "SELECT age, name FROM author"
)
@Entity
public class Author implements Serializable {
    // ...
}
```

다른 방법에 아래 두가지가 더 있다 
- jpa-named-queries.properties 파일 : 네임드 쿼리에서 동적 정렬을 활용할때 권장
- Pageable에서 Sort를 통해 동일한 쿼리 정의 : 네임드 쿼리, 네이티브 쿼리
```

# 네임드 쿼리
# Find the names of authors
Author.fetchName=SELECT a.name FROM Author a
# Find the names and ages of authors
Author.fetchNameAndAge=SELECT a.age AS age, a.name AS name FROM Author a

# 네이티브 쿼리
# Find the names of authors
Author.fetchName=SELECT name FROM author
# Find the names and ages of authors
Author.fetchNameAndAge=SELECT age, name FROM author
```
orm.xml 파일을 통해 동일한 쿼리를 정의할 수 있다.
```

    <query>SELECT a.name FROM Author a</query>
</named-query>

<!-- Find the names and ages of authors -->

    <query>SELECT a.age AS age, a.name AS name FROM Author a</query>
</named-query>
```

#### 스프링 프로젝션 재사용 방법
엔티티가 많은 수의 속성을 갖는 경우, 여러 조합의 속성을 가져오기 위한 여러 읽기 전용 쿼리가 필요하다.  
(예: age/name/genre/email, age/name/genre, name/email 등)  
3개의 인터페이스 기반 닫힌 프로젝션 정의는 실용적이지 않다. 가장 많은 정보를 가져오는 쿼리를 충족시키는 getter들을 포함하는 스프링 프로젝션이 필요하다.
```
@JsonInclude(JsonInclude.Include.NON_DEFAULT)
public interface AuthorDto {
    Integer getAge();
    String getName();
    String getGenre();
    String getEmail();
    String getAddress();
}
```
`@JsonInclude(JsonInclude.Include.NON_DEFAULT)` 어노테이션은 null 값(=현재 쿼리에서 가져오지 않은 속성) 직렬화 제외를 위해 필요하다.  
스프링 데이터 쿼리 빌더 메커니즘을 이용할 수 있다.
```
List<AuthorDto> findBy();
```

또는 JPQL을 작성할 수 있다.
```
    @Query("SELECT a.age AS age, a.name AS name, a.genre AS genre, "
            + "a.email AS email, a.address AS address FROM Author a")
    List<AuthorDto> fetchAll();
```
위 메소드를 활용해 age, name, genre만 가져오는 쿼리, name, email만 가져오는 쿼리에 각각 AuthorDTO 프로젝션을 재사용할 수 있다.
```
    @Query("SELECT a.age AS age, a.name AS name, a.genre AS genre FROM Author a")
    List<AuthorDto> fetchAgeNameGenre();

    @Query("SELECT a.name AS name, a.email AS email FROM Author a")
    List<AuthorDto> fetchNameEmail();
```

## 26.스프링 프로젝션에서 엔티티를 추가하는 방법
어플리케이션에서 스프링 프로젝션 내에서 엔티티를 가져와얗하는 경우가 있을 수 있다.

#### 구체화된 연관관계
양방향 지연 @OneToMany 의 Author와 Book 엔티티가 있다. 스프링 프로젝션은 두 엔티티를 title 속성으로만 매핑해야한다고 가정한다.
```
public interface BookstoreDto {
    Author getAuthor();
    String getTitle();
}
```
데이터 가져오기는 아래와 같이 구현한다.
```
@Repository
@Transactional(readOnly = true)
public interface AuthorRepository extends JpaRepository<Author, Long> {
    @Query("SELECT a AS author, b.title AS title FROM Author a JOIN a.books b")
    List<BookstoreDto> fetchAll();
}
```
```
SELECT
    author0_.id,
    books1_.title,
    author0_.age,
    author0_.genre,
    author0_.name
FROM author author0_
INNER JOIN book books1_
    ON author0_.id = books1_.author_id
```
읽기-쓰기 트랜잭션으로 fetchAll()을 호출한다.
```
    @Transactional
    public List<BookstoreDto> fetchAuthors() {
        List<BookstoreDto> dto = authorRepository.fetchAll();

        // 가져온 Author 인스턴스는 하이버네이트에 의해 관리되는 managed 상태
        // 다음 코드는 UPDATE를 트리거
        dto.get(0).getAuthor().setGenre("Poetry");

        return dto;
    }
```
아래와 같이 출력한다.
```
List<BookstoreDto> authors = bookstoreService.fetchAuthors();
authors.forEach(a -> System.out.println(a.getAuthor() + ", Title: " + a.getTitle()));
```

#### 구체화되지 않은 연관관계
Author와 Book이 구체화된 연관관계가 없으나, genre라는 속성을 공유한다고 가정하자.  
genre 속성은 Author, Book을 조인하고 스프링 프로젝션 BookstoreDto서 데이터를 가져오는데 사용된다.
```
@Repository
@Transactional(readOnly = true)
public interface AuthorRepository extends JpaRepository<Author, Long> {
    @Query("SELECT a AS author, b.title AS title " +
            "FROM Author a JOIN Book b ON a.genre=b.genre ORDER BY a.id")
    List<BookstoreDto> fetchAll();

## 27. 엔티티의 일부 또는 외부 가상 속성을 통한 스프링 프젝션 보완 방법
스프링 프로젝션은 도메인 모델의 일부거나, 그렇지 않은 가상 속성으로 보완될 수 있다.
> 도메인 모델 : 애플리케이션이 해결하려는 특정 문제 영역(도메인)을 추상화한 데이터 및 로직의 집합. 엔티티, VO, 애그리게이트 등  

인터페이스 기반 열린 프로젝션 : 도메인 모델에서 이름이 일치하지 않고 실행 시에 반영되는 결과를 반환하는 메소드를 갖는 인터페이스 기반 스프링 프로젝션
다음 예시 스프링 프로젝션은 가상 속성(years, rank, boks)을 포함하고 있다.
```
public interface AuthorNameAge {
    String getName();

    @Value("#{target.age}")
    String years();

    @Value("#{ T(java.lang.Math).random() * 10000 }")
    int rank();

    @Value("5")
    String books();
}
```
AuthorNameAge는 @Value와 스프링 SpEL을 사용해 도메인 모델에 없는 rank, books 두개 가상 속성을 보완한다.
> SpEL : Spring Expression Language. 
> - target은 SpEL에서 제공하는 변수
> - target은 프로젝션과 매핑된 도메인 모델 인스턴스, 즉 기반 엔티티 객체

```
@Repository
@Transactional(readOnly = true)
public interface AuthorRepository extends JpaRepository<Author, Long> {
    @Query("SELECT a.name AS name, a.age AS age FROM Author a WHERE a.age >= ?1")
    List<AuthorNameAge> fetchByAge(int age);
}

@Component
public class AuthorTransformer {
    public List<AuthorDto> transform(List<Object[]> rs) {
        final Map<Long, AuthorDto> authorsDtoMap = new HashMap<>();

        for (Object[] o : rs) {

            Long authorId = ((Number) o[0]).longValue();

            AuthorDto authorDto = authorsDtoMap.get(authorId);
            if (authorDto == null) {
                authorDto = new AuthorDto();
                authorDto.setId(((Number) o[0]).longValue());
                authorDto.setName((String) o[1]);
                authorDto.setGenre((String) o[2]);
            }

            BookDto bookDto = new BookDto();
            bookDto.setId(((Number) o[3]).longValue());
            bookDto.setTitle((String) o[4]);

            authorDto.addBook(bookDto);
            authorsDtoMap.putIfAbsent(authorDto.getId(), authorDto);
        }

        return new ArrayList<>(authorsDtoMap.values());
    }
}
