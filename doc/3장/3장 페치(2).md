## 항목 30: 스프링 프로젝션을 통한 모슨 속성 가져오는 방법
* Author Entity는 id, age, genre, name 의 4가지 속성을 갖는다.
* 인터페이스 / 클래스 기반 스프링 닫힌 프로젝션을 통해 일부 속성을 가져 오는 것을 배웠다.
* 다양한 방법으로 엔티티의 모든 속성을 가져오는 방법을 알아보자.
  * **읽기 전용 엔티티**
    * JpaRepository의 findAll() 메서드를 통해 읽기 전용 엔티티를 조회한다.
      * AuthorRepository.findAll();
      * 내장 findAll() 메서드는 기본적으로 @Transactional(readOnly = true)로 동작한다.
      * 읽기전용 엔티티는 자동 플러시나 더티 체킹이 없다. 하이버네이트에게 hydrated 상태도 제거하게 한다.
        * 객체 초기화 상태 : hydrated, 연관관계는 loading 정책에 따라 다름
  * **스프링 프로젝션**
    * **인터페이스 기반**
      * 인터페이스 기반 프로젝션은 닫힌 프로젝션이다.
      * getter를 통해 특정한 속성만 가져오고 엔티티의 나머지 속성은 무시되기 때문에 닫혔다고 표현한다.
      * ~~~java
        public interface AuthorDto {
            String getName();
            String getGenre();
            Stirng getAge();
            String getId();
        }
        ~~~
      * 위 인터페이스 기반 닫힌 프로젝션을 가져오는 유형은 아래와 같다.
        * **쿼리 빌더 메커니즘 사용**
        * ~~~java
          @Repository
          @Transactional(readOnly = true)
          public interface AuthorRepository extends JpaRepository<Author, Long> {
            List<AuthorDto> findByName(String name);
          }
          ~~~
          * Author 엔티티를 조회하는 쿼리가 실행되지만 영속성 컨텍스트에는 아무런 엔티티도 로드되지 않는다.
          * 참고로 인터페이스 대신 object[]를 사용할 수도 있지만, 영속성 컨텍스트에 데이터를 로드하기 때문에 효율적이지 않다.
          <hr>
        * **JPQL 및 @Query 사용**
          * ~~~java
            @Repository
            @Transactional(readOnly = true)
            public interface AuthorRepository extends JpaRepository<Author, Long> {
              @Query("select a from Author a")
              List<AuthorDto> findByName(@Param("name") String name);
            }
            ~~~
            * 이렇게 사용하면 동일하게 엔티티를 조회하는 쿼리가 실행되지만 영속성 컨텍스트에는 조회 대상이 되는 엔티티들이 모두 로드된다.
            * 스프링이 인터페이스 기반의 닫힌 프로젝션도 생성해야 하고, 영속성 컨텍스트에 엔티티도 로드되므로 효율적이지 못하다.
            <hr>
        * **명시적 컬럼 목록 및 @Query와 함께 사용한 JPQL**
          * ~~~java
            @Repository
            @Transactional(readOnly = true)
            public interface AuthorRepository extends JpaRepository<Author, Long> {
              @Query("select a.name, a.genre, a.age, a.id from Author a")
              List<AuthorDto> findByName(@Param("name") String name);
            }
            ~~~
            * 이렇게 사용하면 영속성 컨텍스트에는 조회 대상이 되는 엔티티들이 모두 로드되지 않는다.
            * 스프링이 인터페이스 기반의 닫힌 프로젝션도 생성해야 하지만, 영속성 컨텍스트에 엔티티도 로드되지 않으므로 효율적이다.
            <hr>
        * **네이티브 쿼리와 @Query 사용**
        * ~~~java
          @Repository
          @Transactional(readOnly = true)
          public interface AuthorRepository extends JpaRepository<Author, Long> {
            @Query(value = "select name, genre, age, id from author where name = :name", nativeQuery = true)
            List<AuthorDto> findByName(@Param("name") String name);
          }
          ~~~
            * 이렇게 사용하면 영속성 컨텍스트는 조회 대상이 되는 엔티티들이 모두 로드되지 않는다.
            * 스프링이 인터페이스 기반의 닫힌 프로젝션도 생성해야 하지만, 영속성 컨텍스트에 엔티티도 로드되지 않으므로 효율적이다.
            * 속도는 느린 편이다.
          <hr>
* 쿼리 빌더 메커니즘을 사용하는 방법이 가장 효율적이다. JPQL로 모든 필드를 명시하는 방법도 효율적이다.

## 항목 31: 생성자 표현식을 통해 DTO를 가져오는 방법
* 아래와 같은 Author Entity가 있다.
  * ~~~java
    @Entity
    public class Author {
      @Id
      @GeneratedValue(strategy = GenerationType.IDENTITY)
      private Long id;
      private String name;
      private String genre;
      private String age;
    }
    ~~~
* 값을 가져오기 위해 DTO를 사용해보자. 엔티티 속성과 매핑되는 맴버 변수, 생성자를 가진 DTO를 만들어보자.
  * ~~~java
    public class AuthorDto {
      private String name;
      private String genre;
      private String age;
      
      public AuthorDto(String name, String genre, String age) {
        this.name = name;
        this.genre = genre;
        this.age = age;
      }
    }
    ~~~
* 이제 값을 가져와야 한다. 제일 빠르고, 영속성 컨텍스트에 엔티티가 로드되지 않는 방법인 쿼리빌더 매커니즘으로 가져와 보자.
* ~~~java
  @Repository
  @Transactional(readOnly = true)
  public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    List<AuthorDto> findByName(@Param("name") String name);
  }
  ~~~
* 하지만 간단하지 않은 조건을 가져올는 쿼리 빌더보다 @Query를 사용하여 JPQL을 작성하기도 한다. 이때 JPQL에서 엔티티가 아니라 자바 객체를 반환할 수도 있는데 이를 생성자 표현식이라고 한다.
* ~~~java
  @Repository
  @Transactional(readOnly = true)
  public interface AuthorRepository extends JpaRepository<Author, Long> {
    
    @Query("select new path.AuthorDto(a.name, a.genre, a.age) from Author a where a.name = :name")
    List<AuthorDto> findByName(@Param("name") String name);
  }
  ~~~
## 항목 32: 생성자 표현식을 통해 DTO에서 엔티티를 가져오지 말아야 하는 이유
* 책, 작가 엔티티가 장르라는 속성을 공유 한다고 가정한다. 공통속성으로 조인해서 결과를 DTO로 만드는데 이때, 책 엔티티, 작가의 이름 이 두 속성을 갖는다.
  * ~~~
    class bookAuthorDto
      {
          private Book book;
          private String authorName;
      }
    ~~~
* 이 경우 JPQL을 통해 생성자 표현식으로 DTO를 만들어 가져오는 방법을 사용할 수 있다.
  * ~~~java
    @Query("select new path.BookAuthorDto(b, a.name) from Book b join Author a on a.장르 = b.장르")
    List<BookAuthorDto> findBookAuthor();
    ~~~
* 실행하면, 두 개의 쿼리가 발생한다.
* 이때 N+1 문제가 발생할 수 있다. 이는 책 엔티티를 가져올 때마다 작가 엔티티를 가져오기 때문에 발생한다.


## 항목 33: JPA Tuple을 통해 DTO를 가져오는 방법
* Author 엔티티를 조회하고 이번에는 결과를 javax.persistence.Tuple에 담아보자.
  * ~~~java
    @Repository
    @Transactional(readOnly = true)
    public interface AuthorRepository extends JpaRepository<Author, Long> {
      
      @Query("select a.name as name, a.genre as genre, a.age as age, a.id as id from Author a")
      List<Tuple> findByName(@Param("name") String name);
    }
    ~~~
    * Tuple로 이렇게 받으면 DTO를 만들 필요가 없다. 이거 많이 봤다. object[]로 받는거랑 똑같은게 아닐까..
      * 별칭을 유지할 수 있다. object[]로 받으면 별칭을 유지할 수 없다.
        * as name 으로부터 name 값을 유지받을 수 있다.
      * 자동으로 값을 캐스팅 해준다.
      * 자바 제네릭을 지원하므로 Object 보다 타입 안정성이 높다.
    * 위 3 가지로 스칼라 프로젝션 (여러 데이터 타입의 값을 가져오는 방법) 을 가져오는 가장 좋은 방법이라고 말할 수 있다.
    * JPQL, 네이티브 쿼리, Criteria API 에서도 사용할 수 있다.
  * ~~~

    authors.forEach(tuple -> {
      String name = tuple.get("name");
      String genre = tuple.get("genre");
      String age = tuple.get("age");

    ~~~
    * 위 처럼 get 메서드를 통해 값을 가져올 수 있으며, 인자 값으로는 별칭이 쓰인다.
    * instenceof를 통해 타입을 확인할 수 있다.

## 항목 35: ResultTransformer를 통해 DTO를 가져오는 방법
* Author 엔티티의 name, age 속성만 가져올 때 DTO와 하이버네이트의 resultTransformer를 사용해보자.
* 이 인터페이스는 쿼리 결과를 애플리케이션 쿼리 결과 리스트로 변환하는 하이버네이트의 고유 기능이며, JPQl과 네이티브 쿼리와 함께 사용되는 기능이다.
* 첫번째로 DTO를 정의하고, ResultTransformer는 생성자, 혹은 세터가 있는 DTO를 통해 데이터를 가져올 수 있다.
  * **생성자로 가져오는 경우**
    ~~~
    package com.bookstore.dto;

    public class AuthorDtoNoSetters implements Serializable {
        private static final long serialVersionUID = 1L;
    
        private final String name;
        private final int age;
    
        public AuthorDtoNoSetters(String name, int age) {
            this.name = name;
            this.age = age;
        }
    
        public String getName() {
            return name;
        }
    
        public int getAge() {
            return age;
        }
    
        @Override
        public String toString() {
            return "AuthorDto{" + "name=" + name + ", age=" + age + '}';
        }
    }  
    ~~~
  * 이후 AliasToBeanConstructorResultTransformer를 사용하는데 EntityManagere > createQuery > unwrap 메서드를 통해 name, age 속성을 가져올 수 있다.
  * 
      ~~~
      @Override
          @Transactional(readOnly = true)
          public List<AuthorDtoNoSetters> fetchAuthorsNoSetters() {
              Query query = entityManager
                      .createQuery("SELECT a.name as name, a.age as age FROM Author a")
                      .unwrap(org.hibernate.query.Query.class)
                      .setResultTransformer(
                              new AliasToBeanConstructorResultTransformer(
                                      AuthorDtoNoSetters.class.getConstructors()[0]
                              )
                      );
    
              List<AuthorDtoNoSetters> authors = query.getResultList();
    
              return authors;
          }
      ~~~

## 항목 36: 커스텀 ResultTransformer를 통해 DTO를 가져오는 방법
* ResultTransformer는 주로 단일 레벨의 DTO로 변환하는데 적합하고 복잡한 관계형 데이터 구조를 처리하는데는 부족할 수 있다.
* 예시를 보자.
* ~~~
  public class AuthorDto implements Serializable {
    private static final long serialVersionUID = 1L;

    private Long authorId;
    private String name;
    private int age;

    private List<BookDto> books = new ArrayList<>();
  ~~~
* ~~~
    public class BookDto implements Serializable {
      private static final long serialVersionUID = 1L;

      private Long bookId;
      private String title;

    }
  ~~~
* 원하는 결과 셋을 가져오기 위해 transformTuple / transformList 인터페이스 메서드를 통해 구현하면 된다.
* ~~~
  public class AuthorDtoResultTransformer implements ResultTransformer {
    private static final long serialVersionUID = 1L;

    private Map<Long, AuthorDto> authorMap = new LinkedHashMap<>();

    @Override
    public Object transformTuple(Object[] tuple, String[] aliases) {
        Long authorId = (Long) tuple[0];
        AuthorDto author = authorMap.get(authorId);

        if (author == null) {
            author = new AuthorDto();
            author.setAuthorId(authorId);
            author.setName((String) tuple[1]);
            author.setAge((int) tuple[2]);
            authorMap.put(authorId, author);
        }

        BookDto book = new BookDto();
        book.setBookId((Long) tuple[3]);
        book.setTitle((String) tuple[4]);

        author.getBooks().add(book);

        return author;
    }

    @Override
    public List transformList(List collection) {
        return new ArrayList<>(authorMap.values());
    }
  }
  ~~~
* ~~~
    @Repository
    public class Dao implements AuthorDao {
    @PersistenceContext
    private EntityManager entityManager;

    @Override
    @Transactional(readOnly = true)
    public List<AuthorDto> fetchAuthorWithBook() {
        Query query = entityManager
                .createNativeQuery(
                        "SELECT a.id AS author_id, a.name AS name, a.age AS age, "
                                + "b.id AS book_id, b.title AS title "
                                + "FROM author a JOIN book b ON a.id=b.author_id")
                .unwrap(org.hibernate.query.NativeQuery.class)
                .setResultTransformer(new AuthorBookTransformer());

        List<AuthorDto> authors = query.getResultList();

        return authors;
    }
    }

## 항목 37: @Subselect를 통해 엔티티를 쿼리에 매핑하는 방법
* DTO / DTO + 추가 또는 뷰를 통해 엔티티에 매핑하는 여러 가지 가능한 해결 방법을 평가한 후에만 @Subselect를 적용하는 것을 고려해라
* 하이버네이트의 @Subselect를 통해 엔티티를 쿼리에 매핑하는 방법이 있다. 
* @OneToMany 연관관계를 갖는 두 엔티티를 가정해본다.
* ~~~ java
    @Entity
    public class Author implements Serializable {
    private static final long serialVersionUID = 1L;

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String genre;
    private int age;

    @OneToMany(cascade = CascadeType.ALL,
            mappedBy = "author", orphanRemoval = true)
    private List<Book> books = new ArrayList<>();

    public void addBook(Book book) {
        this.books.add(book);
        book.setAuthor(this);
    }

    public void removeBook(Book book) {
        book.setAuthor(null);
        this.books.remove(book);
    }

    public void removeBooks() {
        Iterator<Book> iterator = this.books.iterator();

        while (iterator.hasNext()) {
            Book book = iterator.next();

            book.setAuthor(null);
            iterator.remove();
        }
    }
  }
  
    @Entity
    public class Book implements Serializable {
    private static final long serialVersionUID = 1L;

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;
    private String isbn;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "author_id")
    private Author author;
  }
  ~~~
* 아이디어는, Author 엔티티의 일부 속성과, getBook()를 통해 지연방식으로 book 리스트를 가져오는 것이다.
* 기존 DTO는 관리되지 않고, 연관관계를 탐색할 수 없기 때문에 사용할 수 없다.
* 하이버네이트 @Subselect는 이 문제에 대한 해결책을 제공한다.
  * 불변의 읽기 전용 엔티티를 지정된 sql로 매핑할 수 있다.
  * 이 엔티티를 통해 어플리케이션은 요청 시 연관관계를가져올 수 있으며 아래와 같은 단계를 따른다.
    * Autor에서 필요한 속성만 포함하는 새로운 엔티티를 정의한다.
    * 해당 속성에 대한 getter를 정의한다.
    * 쓰기 작업을 허용하지 않기 위해 @Immutable을 지정한다.
    * @Synchronize를 사용해 엔티티에 대한 보류 중인 상태 전환을 플러시한다.
    * @Subselect를 활용해 필요한 쿼리를 작성한다.
    * 아래와 같은 결과가 나온다.
  * ~~~
    @Entity
    @Subselect(
    "SELECT a.id AS id, a.name AS name, a.genre AS genre FROM Author a")
    @Synchronize({"author", "book"})
    @Immutable
    public class AuthorSummary implements Serializable {
    private static final long serialVersionUID = 1L;

    @Id
    private Long id;

    private String name;
    private String genre;

    @OneToMany(mappedBy = "author")
    private Set<Book> books = new HashSet<>();

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public String getGenre() {
        return genre;
    }

    public Set<Book> getBooks() {
        return books;
    }
    ~~~
  * 이제 일반적인 스프링 레파지토리를 작성한다.
    * ~~~java
      @Repository
      public interface AuthorSummaryRepository extends JpaRepository<AuthorSummary, Long> {
      }
      ~~~
      
  * 서비스에서는 이렇게 사용한다.
    * ~~~java
      @Service
      public class BookstoreService {
      private final AuthorSummaryRepository authorSummaryRepository;

      public BookstoreService(AuthorSummaryRepository authorSummaryRepository) {
          this.authorSummaryRepository = authorSummaryRepository;
      }
  
      @Transactional(readOnly = true)
      public void fetchAuthorWithBooksById(long id, String genre) {
          AuthorSummary author = authorSummaryRepository.findById(id).orElseThrow();
  
          System.out.println("Author: " + author.getName());
  
          if (author.getGenre().equals(genre)) {
              // lazy loading the books of this author
              Set<Book> books = author.getBooks();
              books.forEach((b) -> System.out.println("Book: "
                      + b.getTitle() + "(" + b.getIsbn() + ")"));

## 항목 40: JOIN과 JOIN FETCH 결정 방법
* JOIN / JOIN FETCH는 지연연관관계를 갖고 있지만 일부 데이터는 즉시 가져와야 할 때 역할을 한다.
* 다음 두 상황을 보자.
  * 주어진 가격보다 비싼 book과 이에 해당하는 모든 Author
  * 모든 book과 해당 author
### 주어진 가격보다 비싼 저서를 저술한 모든 저자 가져오기
* 이를 위해 AuthorRepository를 사용한다.
* ~~~java
    @Repository
    @Transactional(readOnly = true)
    public interface AuthorRepository extends JpaRepository<Author, Long> {
    // INNER JOIN
    @Query(value = "SELECT a, b FROM Author a INNER JOIN a.books b " +
    "WHERE b.price > ?1")
    List<Author> fetchAuthorsBooksByPriceInnerJoin(int price);

    // JOIN FETCH
    @Query(value = "SELECT a FROM Author a JOIN FETCH a.books b " +
            "WHERE b.price > ?1")
    List<Author> fetchAuthorsBooksByPriceJoinFetch(int price);
  }
  ~~~
### JOIN FETCH 동작방법
* JOIN FETCH는 JPA 기능으로 하나의 SELECT를 통해 부모 객체로 연관관계를 초기화 한다.

### JOIN 동작 방법
* JOIN은 반대로 연관관계가 SELECT를 통해 부모 객체로 초기화되지 않는다.
* 그러므로 정상적으로 조건에 맞는 저자를 가져오지만, 연관관계에 접근할 시, 추가적인 쿼리가 발생하며 이는 최초에 조건과 맞지 않는다.
  * 조건에 맞는 저자 신원호, 신원호.getBooks()를 호출하면 추가적인 쿼리가 발생한다.
  * select a from book a where a.author_id = '신원호'
  * 그러므로 최초에 조건과 맞지 않는 결과가 나올 수 있다. 추가적인 쿼리를 날릴때는 조건절이 빠졌기 때문이다.

### 모든 저자 가져오기
* 이 경우에는 성능 저하만 있고, 결과는 동일하다. 조건절이 따로 있지 않기 떄문이다.

* 일반적인 원칙으로 데이터를 엔티티로 가져와야 할 때 JOIN FETCH를 사용하고 하이버네이트는 SELECT 절로 연관관계를 포함해야 한다.
* 읽기 전용 데이터를 가져올 때에는 JOIN FETCH 대신 JOIN + DTO를 사용하는 것이 좋다.

## 항목 41: 모든 왼쪽 엔티티를 가져오는 방법
* 하나의 select로 엔티티와 지연 연관관계를 가져오는 것은 JOIN FETCH가 완벽하다는 것을 알았다.
* JOIN FETCH 는 INNER JOIN으로 변환된다.
* JOIN FETCH 대신 LEFT JOIN FETCH 를 사용하면 된다.
